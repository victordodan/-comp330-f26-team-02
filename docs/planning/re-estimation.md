# Re-Estimation

**Team:** Codex Ramblers  
**Project:** CampusConnect  
**Current Phase:** A2 — Planning & Estimation  
**Release Cycle:** Cycle 1  

## Purpose

This document defines when and how Codex Ramblers will revisit Cycle 1 estimates as the project develops.

The estimates in `estimates.md` represent the team's current understanding of the work. They may need to be updated when new information changes the expected effort, schedule, dependencies, or risk.

## Re-Estimation Triggers

The team should review an estimate when:

- a requirement or acceptance criterion is added or materially changed;
- Cycle 1 scope changes;
- a task is larger or more complex than originally expected;
- a dependency causes a significant delay;
- a technical approach creates unexpected complexity;
- a tracked risk occurs or becomes more likely;
- team availability or capacity changes significantly;
- integration or testing reveals additional work;
- a major engineering decision changes the planned approach; or
- actual progress differs significantly from the current estimate.

Minor changes that do not materially affect effort or schedule do not require a full re-estimation.

## Evidence Used for Re-Estimation

When reviewing an estimate, the team should consider the most current engineering evidence available, including:

- `docs/requirements/requirements.md`;
- `docs/requirements/acceptance-criteria.md`;
- `docs/planning/scope.md`;
- `docs/planning/task-plan.md`;
- `docs/planning/estimates.md`;
- `docs/planning/risk-register.md`;
- `docs/planning/schedule.md`;
- GitHub Issues and Project status;
- relevant engineering decisions; and
- completed work or verification evidence.

The team should use current repository evidence rather than relying only on the original estimate.

## Re-Estimation Process

When a re-estimation trigger occurs:

1. Identify the affected requirement, task, estimate, milestone, or risk.
2. Review the new information that caused the estimate to be reconsidered.
3. Compare the new information with the assumptions used for the current estimate.
4. Update the low, likely, and high estimate when the expected effort has materially changed.
5. Review affected dependencies, milestones, risks, and ownership.
6. Update related planning and traceability evidence.
7. Communicate significant changes to the team.

Re-estimation should improve the accuracy of the current plan rather than preserve an estimate that is no longer realistic.

## Planning Updates

A significant estimate change may require updates to:

- `estimates.md`;
- `schedule.md`;
- `task-plan.md`;
- `risk-register.md`;
- `traceability.md`;
- GitHub Issues;
- the GitHub Project; and
- related team commitments or decision evidence.

Only artifacts affected by the change need to be updated.

## Ownership

The owner of the affected work should identify new information that may require re-estimation.

The Planning & Process Lead coordinates significant planning changes, while the relevant artifact owners are responsible for keeping their evidence current.

The Quality & Review Lead should check that significant re-estimation changes remain consistent across related A2 evidence before a phase gate.

## Current A2 Status

The Cycle 1 estimates and schedule represent the current A2 planning baseline.

No estimate should be presented as guaranteed. Low, likely, and high values represent planning ranges based on the team's current information.

Future changes should be documented when a re-estimation trigger materially affects the Cycle 1 plan.

## Review

Codex Ramblers will review re-estimation needs throughout Cycle 1 and before major phase gates.

Before the `a2-planning-estimate` tag is created, the team should confirm that the estimates, schedule, risks, and traceability reflect the current planning baseline.
