# Working Agreements

**Team:** Codex Ramblers  
**Project:** CampusConnect  
**Primary Owner:** Venkata Aravind Mareddy  
**Backup Owner:** Shu Perez  

This document defines the working practices that the Codex Ramblers team agrees to follow while planning, developing, reviewing, integrating, and verifying CampusConnect. These agreements may be updated when the team identifies a better way of working.

## Communication Practices

- Microsoft Teams will be the primary communication platform for the team.
- Team members should acknowledge important messages within 24 hours when possible.
- Questions, blockers, and schedule conflicts should be communicated to the team as early as possible.
- Important project decisions should not exist only in chat. They should be recorded in the appropriate GitHub issue, pull request, or project documentation.

## Work Planning and Ownership

- Project work will be divided into clear tasks with an identified owner.
- GitHub Issues will be used to make significant work and responsibilities visible.
- Each major Assignment 1 artifact will have a primary owner and a backup owner.
- Team members are responsible for keeping the status of their assigned work current.
- If a team member becomes blocked or cannot complete a task, the team should be informed so the backup owner or another team member can assist.

## Git and Branching

- The `main` branch will represent the team's reviewed and integrated work.
- Significant changes should be completed on a separate branch rather than directly on `main`.
- Branch names should clearly describe the work being performed.
- Team members should keep their branches reasonably current with `main` to reduce integration conflicts.
- Completed branch work should be integrated through a pull request.

## Commits

- Commits should be focused on a clear unit of work.
- Commit messages should briefly and clearly describe the change.
- Unrelated changes should be separated when practical.
- Team members should review their changes before committing them.

## Pull Requests and Review

- Significant changes should be submitted through a pull request.
- Pull requests should describe what was changed and reference the related GitHub Issue when applicable.
- At least one other team member should review significant changes before they are merged when practical.
- Review comments should be addressed before merging.
- Pull requests should not be merged when known required checks are failing.

## Testing and Verification

- Changes should be checked before they are considered complete.
- Relevant automated tests and repository checks should pass when available.
- Documentation changes should be reviewed for accuracy, completeness, and working links.
- Verification evidence should be retained in the repository when required by the project.

## Definition of Done

A task is considered done when:

- the agreed scope has been completed;
- the work satisfies its acceptance criteria;
- relevant documentation has been updated;
- applicable tests and checks pass;
- the work has been reviewed when review is required;
- important decisions and AI assistance are documented when applicable; and
- the completed work is traceable to the appropriate GitHub evidence.

## Documentation and Traceability

- Authoritative engineering evidence will be maintained in the GitHub repository.
- Requirements, decisions, planning information, and other project evidence should be stored in their designated repository locations.
- Issues, commits, branches, and pull requests should be linked when practical so that significant work can be traced.
- Documentation should be updated when project decisions or practices change.

## AI-Assisted Work

- AI-assisted work must follow the team's AI-Use Policy.
- Team members remain responsible for reviewing and verifying AI-assisted output before using it.
- Significant AI assistance should be recorded in the team's AI-Use Log according to the agreed policy.
- AI-generated content should not be accepted without human review.

## Handling Defects and Broken Builds

- Defects or broken builds should be communicated to the team promptly.
- Significant defects should be tracked using GitHub Issues.
- The team should avoid merging changes with known failing required checks.
- The person working on the affected change should coordinate with the team when assistance is needed.
- Fixes should be verified before the related issue is considered complete.
  
## Conflict Resolution

- Team members should first discuss disagreements respectfully and try to reach a solution together.
- If a disagreement cannot be resolved, the issue should be discussed with the team lead and the rest of the team.
- Decisions should focus on project requirements, engineering evidence, and the best interests of the project.
- Important decisions resulting from a conflict should be documented in the appropriate GitHub issue, pull request, or decision record.
  
## Working Agreement Changes

- These Working Agreements may be updated as the team gains experience during the project.
- Proposed changes should be communicated to the team and agreed upon before becoming team practice.
- Significant changes should be recorded through the repository so the history remains reviewable.
